### P1：DBマイグレーション（`0005_`）・サーバー管理セッション・九州大学周辺シード基盤
- **作業内容**：
  - `db/migrations/0005_m5_m6_simulated_venue.sql`（前方追加のみ、既存 `0001〜0004` 無改変）の作成：
    - サーバー管理簡易セッション（`simulation.demo_account`, `simulation.demo_session`）
    - プロフィール拡張（`bio`＝AI非入力、内部非公開の年齢・性別、興味/自信タグ、固定グリッドID）
    - 認証トラック（団体法人格認証・責任者権限・専門家資格認証）
    - 横の交流トラック（投稿・コメント・賛同・能動接続・団体カレンダー・団体チャット）
    - 縦の公的トラック（簡易レポート・公的要望/申請・自治体オファー）
    - **企業完全分離テーブル**（`corporate_sponsor`, `corporate_support_plan`, `corporate_support_offer`）
    - **人狼モード分離テーブル**（`demo_werewolf_room`, `demo_werewolf_assignment`）
  - HttpOnly Cookie から既存 `ServerAuthContext` へ解決するサーバー側セッションヘルパー実装
  - 九州大学周辺（伊都キャンパス周辺）の固定グリッド定義（グリッドID ⇄ SRID 4326 座標変換）と、疑似アカウント群・ダミー団体メンバー・複数企業支援プランのシード実装
  - PostGIS モードおよびインメモリフォールバック両方の対応維持
- **完了条件**：
  - 新規・既存 PostGIS DB でマイグレーション適用が成功し、既存 M1〜M4 テストが1件も壊れない。
  - クライアントから `role`/`userAccountId` を渡しても無視され、Cookie セッションのみで権限解決されることをテストで確認。

---

### P2：入口画面（通常／人狼モード選択）・新規登録・固定グリッド選択
- **作業内容**：
  - アプリ入口画面：通常モード／人狼モードの選択（裏方検証ワークベンチは `/workbench` 等へ退避温存）
  - 新規アカウント登録・簡易ログイン画面：
    - 立場選択（一般市民・市民団体・自治体・運営）
    - 名前、任意入力の年齢・性別（内部データ扱いを明記）、興味/自信タグ、自己紹介カード
    - **九州大学周辺の固定グリッド地図クリック選択**（補助で郵便番号入力）
  - 登録・ログイン・現在セッション取得 API
- **完了条件**：
  - 5台の別ブラウザ／端末から同時に別アカウントとして登録・ログインでき、それぞれの立場に応じたダッシュボードへ遷移できる。
  - 他ユーザー向け API レスポンスに年齢・性別が含まれないことをテストで確認。

---

### P3：SNS風共通表層（横の交流フィード・通知欄・能動マッチング）＋ポーリング同期
- **作業内容**：
  - 全立場共通の SNS 風タイムライン（民間投稿・コメント・賛同・自治体オファーが縦横無尽に並ぶ表示）
  - 通知確認欄（マッチング通知、企業支援申し出通知、自治体オファー／回答通知、認証結果通知）
  - 能動マッチング機能（自己紹介カード・投稿からスムーズに接続。未認証／未申請の間は「プラットフォームサポート対象外」を明示）
  - 市民の「宛てがない／紹介希望」状態トグル
  - 5端末同時デモ用の自動ポーリング同期（および操作直後の即時更新）
- **完了条件**：
  - 端末Aで投稿・能動接続・コメントを行うと、数秒以内に端末Bのタイムライン／通知欄へ反映される。
  - 自己紹介テキスト（`bio`）が M2 マッチングおよび M3 AI一次評価の入力に含まれないことをテストで確認。

---

### P4：運営・審査者ダッシュボード（既存M1〜M4直結）＋認証トラック
- **作業内容**：
  - **宛てがない登録者（紹介希望）の把握リスト**と、既存 M2推薦 → M3 AI一次評価 → M1/M4 人間二次審査（自己審査禁止）への直結フロー
  - **市民団体の法人格認証パネル**：未認証の市民団体アカウントからの申請を受け、運営が承認すると団体責任者権限と団体専用機能を解放（ダミーメンバー登録を含む）
  - **専門家の資格認証パネル**：一般市民（`person`）からの資格認証申請を運営が承認し、専門家バッジを有効化
  - 公的支援への誘導操作・監査ログ閲覧
- **完了条件**：
  - 宛てがない市民に対し、AI一次評価→第三者審査承認を経てマッチング通知が届く。
  - 未認証の市民団体が団体専用 API を呼ぶとサーバー側で拒否され、運営の認証後に解放されることをテストで確認。

---

### P5：認証済み市民団体ダッシュボード（カレンダー・メンバー・チャット・簡易レポート）
- **作業内容**：
  - 未認証時のロック表示および運営への団体認証申請 UI
  - 認証後に解放される団体専用機能：
    - **カレンダーによる活動管理**（予定登録・実施記録の追加）
    - **メンバー管理**（デモではダミーメンバーの登録・一覧表示、一般市民役と明確に区別）
    - **メンバーチャットスペース**（団体内部のみ閲覧・投稿可能）
    - **活動実績の集計 → 簡易レポート作成**（カレンダー実施記録・SNS活動投稿・専門家助言を束ねて透明化レポートを生成）
- **完了条件**：
  - 未認証団体→運営認証→専用機能解放→カレンダー登録・メンバー確認・チャット・簡易レポート生成の一連の流れが動作する。
  - 団体外ユーザーからメンバーチャット API が閲覧拒否されることをテストで確認。

---

### P6：縦の公的つながり（自治体ダッシュボード）＋企業疑似支援の自動通知
- **作業内容**：
  - **自治体ダッシュボード**（各アカウントへアクションをかける管理画面）：
    - 受け皿：団体からの要望・公的申請・簡易レポートを受信し、受理／質問／条件付き承認／支援決定／差戻しを実行
    - 発信側：特定のアカウント（団体・市民・専門家）や全体へオファー・提携申し出・支援案内を送信
    - 公的承認過程の可視化ビュー（設定フラグ `PUBLIC_APPROVAL_VISIBILITY` によりデモ時は過程公開、実運用時は結果のみへ切替可能な設計）と `ops_audit` への原子記録
  - **企業分離領域の自動支援通知**：
    - 複数の疑似支援プラン条件を評価し、条件合致した団体・活動へ自動で「企業からの支援申し出通知」を発行
- **完了条件**：
  - 団体が簡易レポート付きで申請 → 自治体が承認・回答 → 承認過程ログが可視化され、団体の通知欄へ反映される。
  - 自治体が特定アカウントへオファーを送信 → 対象アカウントの通知欄へ届く。
  - 条件を満たした団体へ疑似企業プランから自動で支援申し出通知が届き、`simulation.actor` テーブルには企業レコードが混入しないことをテストで確認。

---

### P7：人狼モード（分離ラッパー）＋5端末通し検証・Vercelデプロイ確認
- **作業内容**：
  - 入口から入る **人狼モード**（本体ドメインから分離）：
    - 運営役のみ据え置き、参加者が入室すると運営の操作で残りの役柄（一般市民／専門家候補／市民団体／自治体）を抽選割当
    - 抽選結果が各端末のセッションへ反映され、自動的に専用ダッシュボードへ切り替わる
  - 第1部（班メンバー5人実演）および第2部（人狼モード体験）の通しシナリオ検証
  - `pnpm typecheck && pnpm test && pnpm build` 全パス確認および `https://satoyama-nexus.vercel.app/` での実機5端末動作確認
- **完了条件**：
  - 第1部・第2部の両デモが 5 端末同時接続＋ポーリングで破綻なく完走できる。
