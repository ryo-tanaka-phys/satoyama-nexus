## 1. 背景と目的

現在の M1〜M4 ワークベンチは、マッチング計算・AI一次評価・人間二次審査・自己審査禁止・監査ログといった**裏方のガバナンス機構を検証する画面**である。

本拡張の目的は、**学生・講師に向けたライブデモンストレーション**において、それぞれの役割に扮した複数人が実際に登録・交流・要望提出・自治体との公的やり取りを行う **「里山協働の実際の場の模擬」** を、一般人でも直感的に操作できる **SNS風の簡易UI** として成立させ、見せることにある。

---

## 2. 継承する不変条件（前提）

1. **公開リポジトリ前提（要件2・7）**：秘密情報・個人情報・実在主体の非公開情報をリポジトリ・ログ・デモデータへ含めない。
2. **公開カタログと模擬領域の厳格分離（要件3・D03）**：九州大学周辺の活動・団体・自治体・企業はすべて**架空の模擬データ**として `simulation` 領域に保持し、実在主体と混同しない。
3. **外部連絡なし（要件5）**：模擬の通知・申請・オファー・企業支援申し出はすべてアプリ内処理とし、メール・外部API等の実連絡を行わない。
4. **AI一次評価＋人間二次審査の厳守（要件4・D06）**：厳格審査ルート（宛てがない人の仲介・公式協働案件）では、AI出力のみで承認・遷移させず、自己審査禁止・追記型監査を維持する。

## 3. デモ実施形式とモード分離

### 3.1 対象と端末構成
- **観客**：学生・講師。
- **操作環境**：班メンバー **5人** が各自の端末を操作し、仮デプロイ環境（`https://satoyama-nexus.vercel.app/`）上の同一データベースを通じてリアルタイム連動を実演する。
- **同期方式**：端末間の状態反映は **ポーリング** とする。

### 3.2 2部構成デモとモードの分離
アプリの入口で以下の2モードを選択可能とし、**体験用デモ機構（人狼モード）をシステム本体から分離**する。

1. **通常モード（本体）**
   - 登録時に利用者自身が立場を選択する本来の運用形態。
   - **第1部（実演デモ）**：班メンバー5人が以下の固定配役で通し実演を行う。
     1. 一般市民
     2. 専門家（区分上は一般市民枠＋運営からの資格認証）
     3. 市民団体（未認証スタート → 運営の団体認証で専用機能解放）
     4. 自治体（公的機関）
     5. 運営・審査者（裏方・据え置き）
2. **人狼モード（体験デモ用・本体から分離）**
   - **第2部（参加型体験）**：**運営役のみ据え置き**とし、他の参加者に対して抽選で役柄（一般市民／専門家候補／市民団体／自治体）をランダムに割り振る。
   - あくまでデモ用の体験ラッパーであり、大本のシステム仕様・厳密性制約を破壊しない形で分離する。

## 4. 舞台設定・登録情報・プライバシー方針

### 4.1 舞台設定と本拠地入力
- **舞台**：**九州大学周辺（伊都キャンパス周辺）** を想定した架空の里山活動・疑似アカウント群をデータベース上に事前配置する。
- **本拠地入力（デモ仕様）**：将来的な広域地図対応を見据えつつ、デモでは **九州大学周辺の固定地図** を用いる。利用者に複雑な入力を強いず、**固定地図をグリッドで区切った区画をクリック選択**（必要に応じて郵便番号補助）することで、内部的に中心座標（実数値：緯度・経度）として登録する。

### 4.2 アカウント登録項目
アカウント新規作成機能を備えつつ、背景コミュニティとなる疑似アカウント群をDBに事前シードすることで大量登録を不要にする。

| 項目 | 必須/任意 | 用途・公開方針 |
|---|---|---|
| 立場（ロール） | 必須 | 登録時に選択（人狼モード時は抽選割当）。立場に応じたダッシュボードを表示 |
| 名前（表示名） | 必須 | 交流・通知・プロフィールに表示 |
| 年齢 | 任意（入力自由） | **内部データ扱い**（他利用者へ非公開） |
| 性別 | 任意（入力自由） | **内部データ扱い**（他利用者へ非公開） |
| 本拠地 | 必須 | 固定グリッド選択 → 実数値座標へ変換し、地理マッチングに使用 |
| 興味のある分野（タグ） | 必須/推奨 | マッチング円滑化のための構造化タグ |
| 自信のある分野（タグ） | 任意/推奨 | マッチング円滑化・専門性把握のための構造化タグ |
| **自己紹介入力カード** | 任意（全立場共通） | **AIマッチングには使用しない**。人間同士が相手を見て選ぶ**能動マッチング専用** |

## 5. 主体区分と認証モデル

### 5.1 専門家の扱い
- 区分上は **一般市民（`person`）枠** とする（ADR 0002 の決定を継承）。
- 運営が **資格認証** を行うことで、認証済み専門家としてのバッジ付与・専門相談対応が有効になる。

### 5.2 市民団体の扱い（「法人格」認証モデル）
- **本来の構造**：市民団体でしか行えない管理・活動機能（カレンダー活動管理、メンバー管理、メンバーチャット、活動実績の透明化レポート作成、自治体への公的申請、プラットフォームのサポート対象化）を明確に定義し、それらへアクセスするためには **運営の認証（法人格のような位置づけ）** を必要とする。
  - 申請した個人に対して、運営が **団体認証＋団体責任者認証** と **団体メンバー登録権限** を付与する構造とする。
- **デモでの運用**：
  - 市民団体役は1人にまとめて担当させ、**未認証（団体専用機能ロック状態）からスタート**し、デモ中に運営から認証を受けることで専用機能が解放される流れを見せる。
  - 団体メンバーはデモ上は **ダミーデータとして登録するのみ** とし、別端末から操作しない（一般市民役と明確に区別する）。

### 5.3 企業（疑似アカウント・完全分離）
- 将来の本番運用ではダッシュボードやアカウント管理の規模・性質が他アカウントと異なるため、**疑似アカウントとしての企業は他主体から完全分離**して管理する。
- デモ中は人間が操作せず、DB上に **複数の条件付き支援プラン**（「企業はこういう活動を支援したい」という条件定義）を用意する。
- 条件に合致する団体・活動に対して、**企業側からの支援申し出通知が自動で正しく届く**ことを可視化し、企業側も含めてプラットフォームが成立することを実証する。

## 6. 交流・マッチング・公的つながりの要件

### 6.1 「横の交流」と「縦のつながり」（内部区別 × 体験は縦横無尽）
- **横の交流（非公的立場同士）**：市民・市民団体・専門家によるフラットな情報共有、相談、参加表明、協力。
- **縦のつながり（公的立場・支援側との双方向）**：
  - 民間 → 公的：必要に応じた公的支援への誘導、書類申請、支援・バックアップ・資金供与・監査に向けた **サイト上の活動ログ蓄積（活動実績の透明化・簡易レポート作成）**。
  - 公的・企業 → 民間：自治体からのオファー・公募・支援案内、企業からの提携・資金支援の申し出。
- **UI方針**：内部データ・権限・監査上は「横（非公的）」と「縦（公的）」を厳格に区別するが、実際の画面上の交流は縦横無尽に行き来できるSNS風の体験とする。

### 6.2 マッチングの二経路（能動 vs 宛てがない人）
1. **能動マッチング（自分から繋がるルート）**
   - 自己紹介カードや投稿を見て、利用者が自らスムーズに接続できる。
   - ただし、**正式な団体認証・活動申請を受けない限り、プラットフォームとしての公的サポート対象外**であることを明示する。
2. **宛てがない人の仲介（厳格審査ルート）**
   - 接続先の宛てがない登録者は、運営側がその存在・条件を把握した状態からスタートする。
   - 既存の厳格ルール（**M2推薦 → M3 AI一次評価 → 人間二次審査・自己審査禁止**）を経て承認されたうえで、利用者へマッチング通知を届ける。

### 6.3 公的アカウントの承認過程の可視化
- **デモ仕様**：自治体・運営による承認・却下・認証・支援判断の過程を画面上で可視化する。
- **実運用時の扱い（未確定）**：本番環境で過程まですべて公開するか、内部監査ログとして保持しつつ一般には結果のみ確認可能とするかは **未定** とする。設計上、監査ログの保存と公開表示の粒度を分離する。

## 7. 役割別ダッシュボード要件

すべての立場に共通して **SNS風交流フィード**、**通知確認欄**（マッチング通知・企業支援申し出通知・自治体オファー/回答通知）、**自己紹介入力カード** を備える。

| 立場 | ダッシュボードの必須機能 |
|---|---|
| **一般市民** | ・自己紹介カード、興味/自信タグ・固定グリッド本拠地設定<br>・SNS風交流フィード、マッチング通知確認欄<br>・能動マッチング接続（未申請サポート外表示あり）<br>・「宛てがない／紹介希望」状態の表明（運営把握リストへ連携） |
| **専門家**（市民枠＋資格認証） | ・一般市民の全機能<br>・運営への資格認証申請、認証済みバッジの表示<br>・自信のある分野タグに合致する相談・活動への技術助言 |
| **市民団体**（運営の団体認証で解放） | ・未認証時：団体認証申請パネル（専用機能はロック表示）<br>・認証後解放される専用機能：<br>　- **カレンダーによる活動管理**（予定・実施記録）<br>　- **メンバー管理**（デモではダミーメンバーを登録・表示）<br>　- **メンバーチャットスペース**（団体内専用）<br>　- **活動実績ログの蓄積と簡易レポート作成**（自治体向け透明化）<br>　- 自治体への要望・公的申請提出、企業支援申し出／自治体オファー受信 |
| **自治体（公的機関）** | ・窓口紹介カード<br>・**各アカウントへアクションをかける管理画面**：<br>　- 申請・要望・簡易レポートの受け皿（受理・質問・承認・支援決定・差戻し）<br>　- 各アカウント（市民団体・市民等）へのオファー・公的支援案内・提携申し出の発信<br>・承認・回答履歴の可視化 |
| **運営・審査者**（据え置き） | ・宛てがない登録者の把握リスト<br>・既存厳格審査パネル（M2推薦 → M3 AI一次評価 → 人間二次審査・監査ログ確認）<br>・**市民団体の認証**（法人格・責任者認証付与）および **専門家の資格認証**<br>・必要に応じた公的支援への誘導<br>・企業支援プランの条件マッチ通知状況の確認<br>・（人狼モード時のみ）参加者の抽選・役柄配布コントロール |
| **企業**（疑似・分離・操作なし） | ・操作画面なし（DB上の複数支援プランから条件一致時に自動通知を送出） |

## 8. 保留中の細部・未確定事項

### フレーム構築後に詰める細部（保留）
- 九州大学周辺固定地図のグリッド分割数・区画名・具体座標マッピング
- 興味のある分野／自信のある分野のタグ語彙リスト
- 企業支援プランの具体的なプラン名・条件数値・文面
- 事前シードする疑似アカウント・ダミー団体メンバーの人数と設定
- SNS風UIの細かな画面レイアウト・文言・デモ台本

### 未確定事項（将来判断）
- 公的アカウント（自治体・運営）の承認過程を実運用時にどこまで一般公開するか（結果のみ公開 vs 過程公開）
- 広域地図への拡張方針、本番認証プロバイダ、実在公開データの収集・利用条件
- 企業向けの本番アカウント登録・専用ダッシュボード仕様
